# Implement User Authentication and Account Management

Extend the existing admin management system with user authentication, registration, and account management.

Keep the implementation simple, lightweight, and consistent with the existing project.

## 1. Technical Requirements

- Use the existing technology stack, project structure, and UI components.
- Frontend: Vite + React + Material UI.
- Preserve `ssr: false`. The application does not have to be strictly SPA.
- Do not modify the existing MUI Theme.
- Do not redesign or restructure the existing Admin page.
- Reuse existing components, APIs, database models, and state management wherever possible.
- Avoid unnecessary dependencies, complicated permission frameworks, and overengineering.
- Implement authentication and authorization on both frontend and backend.

## 2. User Roles

The system has only two roles: **Admin** and **User**.

### Admin

- Automatically created during initial system setup.
- Default password: `yyytttqqq`.
- Cannot be registered publicly.
- Has full access to all Accounts and Users.
- Can create, edit, and delete Accounts and Users.
- Can manage registration settings, invitation codes, user roles, and passwords.
- Can own multiple Accounts.
- The built-in Admin cannot be deleted.
- Prompt the Admin to change the default password after the first login.

### User

- Can register through the login/registration page.
- Can own at most one Account.
- May exist without an Account.
- Can only access and manage their own Account.
- Can update their own profile and password.
- Cannot access administrative features.

**Important:** `User` refers to the authentication identity, while `Account` refers to the existing business account entity. Keep them logically separate.

## 3. Account Ownership Rules

- Every Account must belong to exactly one User or Admin.
- A regular User can own zero or one Account.
- An Admin can own multiple Accounts.
- Orphaned Accounts are not allowed.
- New Accounts must automatically belong to the currently authenticated User or Admin.
- Do not implement manual account assignment, ownership transfer, or unlinking.
- Deleting a User must also delete all Accounts owned by that User.
- When deleting an Account, display a confirmation dialog with a **"Also delete associated User"** checkbox, checked by default (`true`).
- If the Account belongs to an Admin, deleting it must never delete the Admin.
- If an Account is deleted while retaining its User, that User becomes an empty User without an Account.
- Enforce these ownership constraints on the backend.
- Ensure all cascading deletion operations are handled atomically.
- Prevent role changes that would violate Account ownership constraints.

## 4. Authentication and Registration

Implement simple Login and Registration pages.

Authentication requirements:

- Username and password authentication.
- Persistent login sessions.
- Logout functionality.
- Redirect unauthenticated visitors to the login page.
- Show the appropriate interface after authentication based on the user's role.
- Store passwords securely using password hashing.
- Validate authentication and permissions on all protected backend endpoints.
- Never rely exclusively on frontend permission checks.

### Registration Modes

Admin can select one of three registration modes:

1. **Disabled** — New registration is not allowed.
2. **Invitation Only** — Registration requires a valid invitation code generated by Admin. Invitation codes are single-use by default.
3. **Open Registration** — Anyone can create a User account.

Requirements:

- Registration settings must be persisted in the database.
- Changes must take effect immediately.
- New registrations always receive the `user` role.
- Newly registered Users initially have no associated Account.
- Admin can generate, view, and delete invitation codes.

## 5. Admin Interface

**Preserve the existing single-page Admin interface, including its overall layout, Header, Account List, existing actions, and behavior.**

Do not create a separate Admin dashboard or replace the current management page.

### Header

- Keep all existing Header functionality.
- Add a **Settings** button to the existing Header.
- Clicking Settings should open a Material UI Dialog or Drawer rather than navigate to a separate page.
- Settings should include:
    - Registration mode configuration.
    - Invitation code management.
    - Management of Users without Accounts.
    - Admin password management.
    - Logout.
- Keep the Header compact and consistent with the current design.

### Account List

Extend the existing Account List instead of replacing it.

Requirements:

- Display the User associated with each Account.
- Display the associated User's role (`admin` / `user`).
- Preserve all existing Account information, status indicators, and actions.
- Do not remove or replace any existing Account status fields.
- Integrate the new User information naturally into the existing list layout.
- Maintain the current information density and visual style.
- Do not add account searching or filtering.
- Do not introduce a separate User List page.

### More Menu

Keep the existing **More** menu for each Account.

Add User-related management operations directly into the existing menu.

**The More menu must remain a single-level menu. Do not implement nested menus, cascading menus, or submenus.**

Use Material UI `Divider` and `ListSubheader` to visually separate different groups of actions.

Suggested structure:

```text
More
────────────────────────
ACCOUNT ACTIONS
  Existing Action 1
  Existing Action 2
  ...
────────────────────────
USER ACTIONS
  View User Info
  Edit User
  Reset Password
  Change Role
  Delete User
```

Requirements:

- Preserve all existing More menu actions and behavior.
- Use a single Material UI `Menu`.
- Use `ListSubheader` to identify action groups.
- Use `Divider` to separate groups.
- All actions must remain at the same menu level.
- Do not create hover-based or click-based submenus.
- Keep menu items compact and visually consistent.
- Open relevant Dialogs for User operations.
- Dangerous actions must require confirmation.
- Deleting a User must clearly indicate that all associated Accounts will also be deleted.
- Disable or hide operations that cannot be performed on the built-in Admin.
- Refresh the relevant UI state after operations complete.

Users without associated Accounts should be manageable through a compact section within Settings, since they cannot appear in the Account List.

## 6. User Interface

Create a separate, simplified interface for regular Users.

Do not simply reuse the full Admin interface with hidden administrative buttons.

The User interface should provide:

- View the associated Account and its current status.
- Create an Account if none exists.
- Edit or delete the associated Account.
- Access existing Account functionality where permitted.
- Update personal profile information.
- Change password.
- Logout.

If the User has no Account, show a compact empty state with a clear Account creation action.

Do not expose other Users' Accounts or administrative functionality.

## 7. UI and Layout Requirements

The overall design should prioritize **information density, available screen space, and usability**.

- Keep the main interface within `100vw × 100vh` whenever practical.
- Minimize the vertical space consumed by Headers, titles, and navigation.
- Avoid oversized headings, excessive padding, decorative cards, and unnecessary whitespace.
- Dedicate as much screen area as possible to Account information, status indicators, and controls.
- Prefer internal scrolling for long content instead of making the entire page excessively tall.
- Use compact Material UI components.
- Admin interface: prioritize operational efficiency and information visibility.
- User interface: prioritize simplicity and ease of use.
- Support desktop and mobile/touch layouts.
- Preserve the existing Theme, spacing conventions, and component styling.
- Avoid unnecessary animations and visual effects.

## 8. Implementation Guidelines

1. Inspect the existing architecture, Account data models, authentication-related code, Header, Account List, and More menu before making changes.
2. Extend the existing application incrementally rather than rebuilding it.
3. Reuse existing business logic and Account APIs whenever possible.
4. Make only the necessary database schema changes.
5. Preserve existing Account data and functionality.
6. Enforce role permissions and Account ownership on the backend.
7. Ensure destructive operations require confirmation and maintain database consistency.
8. Do not implement complex RBAC, organizations, additional roles, or unrelated functionality.
9. Do not generate test files or automatically execute tests.
10. Keep all relevant documentation under `docs/`.
11. Favor straightforward, maintainable code over unnecessary abstractions.

## Final Objective

Deliver a fully integrated authentication and Account management system while preserving the existing Admin single-page experience.

The Admin interface should require only minimal structural changes:

- A new Settings button in the existing Header.
- Associated User information in the existing Account List.
- User management actions grouped within the existing single-level More menu using Dividers and Subheaders.

Regular Users should receive a separate, lightweight interface for managing their own Account.

Keep the implementation minimal, secure, visually consistent, and focused on existing functionality.
